# Security policy

Goblin Horde runs on your own computer. Its agent monitor shows agent activity from local sources, and its pet game counts finished work from T3 Code's local database. Some of that activity can be private, so we take reports about exposure seriously.

## Reporting a vulnerability

Please report privately first:

1. **Preferred:** use GitHub's private vulnerability reporting for this repository (**Security** tab → **Report a vulnerability**) once it is enabled.
2. **If that option is not available yet:** open a regular issue titled "Security contact request" that says only which area is affected (for example "phone pairing" or "Claude Code hook receiver"). **Do not include** exploit details, proof-of-concept code, or real data. A maintainer will reply with a private way to share the details.

Please give us a reasonable chance to fix the problem before disclosing it publicly. There is no bug bounty.

Supported version: the latest code on the default branch. Older ZIP packages are not patched separately; reinstall from current source.

## In scope

- **Local network phone pairing.** Phone access is off by default: the viewer listens only on `127.0.0.1` until the person turns phone access on (`phone.json` in the state folder). Then it also listens on one private Wi-Fi address (or `LAN_IP`, honoured only while phone access is on), skipping VPN and virtual adapters and, on Windows, networks marked Public, with pairing required. A paired phone can read the listed chats as summaries, send replies, and approve or decline Codex commands and file changes (Codex's questions are answered on this computer only); it can never turn phone access on or off, make a new pairing code, change Claude Code settings, or change sign-in startup. Turning phone access off or making a new pairing code signs every phone out. Relevant issues include bypassing the 8-character pairing code or its attempt limit (five failures per address per ten minutes), session cookie theft or fixation, the pairing code being exposed to non-local requests, Host or Origin checks that let another site or device read chats or send replies, a phone reaching a local-only route, any listener on a non-loopback address while phone access and the shared pet game are both off, and the server binding to a public address.
- **Source adapters.** How Goblin Horde reads Codex (`codex app-server`), Claude Code hooks (`claude-hook.mjs` and the recorded activity file), Orca (`orca` CLI snapshots), and extension feeds (`EXTENSIONS.md`). Relevant issues include recording or displaying data the README says is not shown (for Claude Code: recording tool output, file contents, error text; for every source: reasoning anywhere but the task view on this computer; on a phone: command output, tool arguments, Codex's reason for an approval, and the words of what an agent asks, is running, or plans, wherever they appear (its `ask`, `now`, `progress`, or `waitingOn`, the questions in its turn states, the lines of its messages that ask a question and the options under them, or a Codex question request), of which a phone gets only kinds, counts, and times), the viewer reading an agent's transcript or chat records for anything but showing that agent (or naming a Claude Code session in view from the title records at its transcript's end and the first prompt at its start) on this computer, credential-like text passing the redaction that every text field goes through before it is recorded or leaves the server, an extension feed injecting raw commands or markup into the viewer or widget, and path or file name handling that reads or writes outside the Goblin Horde state folder.
- **The pet game.** The viewer reads T3 Code's own database (`~/.t3/userdata/statev2.sqlite`, or the file that `GOBLIN_T3_DB` names) read-only through the SQLite built into Node.js, and never writes it. Its one query selects statuses, finish times, ids, and token counts. The counts are taken out of T3 Code's JSON inside SQLite, so no prompt, message, title, or other payload text reaches JavaScript, and an id leaves the reader only as a 16-character hash. A database whose tables or columns are not the expected ones is not read at all. `doctor` opens the same database the same way and prints only the verdict and the file's path. The saved game (`pets.json` and `pets.json.bak` in the state folder) holds numbers, a date, and the hashes of the most recently paid work. Each number is held to what a game can reach: counts are whole numbers within fixed limits, amounts are at most a million million, and a saved game whose horde power or prices would not be numbers is not loaded. A count that only this game's size limits is cut down to it and never refused: more bosses cleared than the game has are held to the bosses there are, and a rerun of a boss the game no longer has is dropped. A saved game is never replaced by a new game. When `pets.json` cannot be read as a saved game and its backup can, the game goes on from the backup. When neither can, no game starts, the viewer says so (`ready: false`), and nothing is written. A file that could not be read is kept, when a start is refused over it and before a save replaces it, as `pets.json.unreadable.<milliseconds>-<random letters>`: a copy with a name of its own, made only where no file has that name, made once for the same bytes, and private to this account, which it is made while it is still empty. A new game begins only in a state folder with neither `pets.json` nor `pets.json.bak`. On the viewer's own listeners, `GET /api/pets`, `POST /api/pets/buy`, and `POST /api/pets/fight` answer this computer only (403 for a paired phone), and the two POSTs take the same local, Origin, and JSON checks as the other local routes. A paired computer on the person's tailnet reaches them only through the shared listener described below, and only once the person turned it on. Only one viewer runs a saved game: it holds `pets.lock` in the state folder (its process id, start time, and port, nothing else) and touches it every five seconds, and a second viewer on the same state folder never loads or saves the game. A lock that has shown an observer no heartbeat for 20 seconds is free whatever its process id says, since Windows hands a freed process id to the next program. A heartbeat is any change of the lock file's modified time, and the 20 seconds are counted on the observer's own monotonic clock. The file's date is never read as a time, so a date an hour ahead does not keep a lock and a date an hour behind does not free one. One look therefore never frees a lock whose process id is alive. Whoever asks for the lock watches it, a starting viewer and `pets-adopt` and `pets-host` alike: a holder that runs shows its heartbeat within five seconds and keeps the lock, and one that shows none for 20 seconds loses it. A viewer that stops gives the lock up only after its last save has landed, and a save asks for the lock again right before each file is put in place. So that goblins can stand on open windows, the pet field asks the Windows API which top-level windows are visible and where each one's rectangle is. For this it never copies a window's title and never asks for the name of the program that owns a window. It asks only how long a title is, compares a window's class with the shell's own classes and then drops it, and compares the owning process id with its own. A window is kept in memory as four numbers and a salted hash of its handle, with a new salt on every run, and nothing about windows is written to disk. The pet field also asks how long ago the last key press or pointer move was (a number of milliseconds, never which key) and whether a full-screen window is in front. None of this is sent anywhere. Opening the task view is separate from the game: it looks through the visible windows' titles for the task view's own window, to bring that window forward, and keeps none of them. Relevant issues include payload text, a window title, or a program name reaching JavaScript, the screen, a log, or the saved game; any write to T3 Code's database; a phone or another site reaching the game's routes; and anything about the game leaving the computer.
- **The shared pet game.** Off by default. `pets-host enable` (`shared.json` in the state folder) makes the viewer open one more listener, on this computer's own Tailscale IPv4 address (100.64.0.0/10) at the viewer's port. It never listens on a Wi-Fi or wired address or on every address, and a saved address that is no longer this computer's Tailscale address keeps it closed. The address is the one this computer's own `tailscale` program names: `tailscale ip -4` gives it, `tailscale status --json` must say Tailscale is connected and list the same address, and an adapter must have it. No adapter's name or address stands in for the program's word, because an internet provider can hand out addresses in the same range. When the `tailscale` program is not found or does not answer, there is no listener, and `pets-host enable`, `pets-host status`, and `doctor` say so. The address is asked for when the listener opens, which every start of the viewer does, and again every 60 seconds while the listener is open. It is not watched in between: when Tailscale gives the computer another address, the listener closes at the next of those checks, the reason is logged, and it stays closed until `pets-host enable` is run again or the old address is back. It is a server of its own with its own handler, so it answers five routes and no other route the viewer has: `POST /api/pair`, `GET /api/pets`, `POST /api/pets/buy`, `POST /api/pets/fight`, and `GET /api/pets/whoami` (which answers `{"ok":true}`). Every request must pass, in order: the peer address its socket reports is in 100.64.0.0/10 or fd7a:115c:a1e0::/48 (a forwarded header is never read); the Host header is the listener's address or one of the MagicDNS names `tailscale status` gives for this computer, with its port; the request's path, exactly as it was sent and with nothing normalized, is one of the five, so `/x/../api/pets`, `/api%2Fpets`, and `/api/pets/` are no route; `tailscale whois` names the peer's login as this computer's own, for every request (a verdict is kept for 60 seconds, a failed lookup refuses, and a tagged device never passes); a POST carries the listener's own Origin; and, for the three game routes, a session cookie earned at `POST /api/pair` with the pairing code (five wrong tries per address per ten minutes). Pairing is bounded: an address holds one session, at most 32 sessions live, an address may earn eight new sessions in ten minutes, and at most 1,024 addresses are tracked, where a full table refuses a new address and never forgets one that used up its tries. An address that is signed in and gives the code again is answered the session it has, with nothing new made and nothing counted. So the programs on one computer share one session, and the check `pets-join` makes never signs a running display out. The pairing code is the one phone access uses, but a session earned on one listener opens only that listener. `pets-host disable` is applied through the viewer that runs on the state folder, which the manager finds by `pets.lock`, by the last start's record, or on its own port. It reports that every computer is signed out only when that viewer's answer says all three things: the shared game is off, nothing listens, and no session is left. An answer that leaves one of them out confirms nothing. Every request the manager and the saved game's lock make to a viewer on this computer has one deadline for the whole exchange, so a viewer that sends half an answer, or sends it a byte at a time, is given up on, and the manager changes nothing when a viewer holds the saved game and does not answer. A listener also reads `shared.json` again before every answer and every three seconds, and closes itself and ends its sessions once the file no longer turns it on, so a change made any other way takes effect too. A `shared.json` that cannot be read is not an off, since that is what a file looks like in the middle of a write: the last choice that could be read stands for 30 seconds while the file is read again every second. After that the listener closes and its sessions end, and it opens again once the file can be read and says on. A new pairing code signs every paired computer out. What crosses the connection is, from a display, pairing requests (the pairing code in the body of `POST /api/pair`), the session cookie, the number of the last event it has shown, and game actions (the kind of a purchase, the number of a boss to fight), and, from the host, the game's three answers. Each answer is cut down to a fixed set of fields by the host before it is sent and again by the display before it is shown: numbers, true and false, a run's name of eight hexadecimal characters, a date, and short codes from fixed lists that say why a game is not ready, why work is not counted, or why a request was not done. No sentence crosses. A host sends a code and never its own words. On a display, a code that is not on its list reads "error", a sentence a host sent is dropped unread, and each code is said in a sentence of the display's own. For an answer with a sentence and no code, as a host of an older version sends, a display shows its own plain sentence and none of the host's words. An answer that holds the pairing code is not sent by a host and not passed on by a display. The code is looked for in every field's name, text, and number, with case, spaces, dashes, and every other character that is not a letter or a digit taken out first, and across the values that follow one another. A display (`pets-join`, which writes `remote.json` and `remote-code.txt`) opens no saved game and forwards its three local pets routes to the host. It sends the code only to a Tailscale address written as four plain decimal numbers, or to a name that resolves to one. A host written as any other kind of number (hexadecimal, octal, a single integer, a short form), an IPv6 address, or a name made only of digits and the letters a to f and x is refused before anything is sent, and the connection is made to exactly the host that was checked. A display never follows a redirect or uses a proxy, gives up on a host at one deadline whatever the host sends meanwhile (a `101` answer included), never repeats a host's own words in a message, takes the code from a file or standard input and never from the command line, and never logs or prints it. `remote-code.txt`, `pairing-code.txt`, and `shared.json` are written so that only this account can open them. On Windows the file's inherited permissions are removed with `icacls`, this account is given the file, and the permissions are read back before the text is written; when anyone but this account, SYSTEM, and Administrators is still in them, the file is not written. Elsewhere the file has mode 0600 and the mode is read back. A file that was there already, left by an older version or another program with its folder's permissions, is made private where it is, and its permissions are read back: `pairing-code.txt` when the shared game is turned on, `pairing-code.txt` and `shared.json` every time before the shared listener opens, and `remote-code.txt` before a display that starts reads its code. When a file cannot be made private, the host does not listen, or the display shows no game and sends its host nothing, and each names the file. The pairing code leaves a computer in one way only: from a display to its host when it pairs, to an address checked as on the tailnet. It is shown on a screen only on the host itself, in two places: `pets-host code` prints it to a terminal on this computer, and the phone pairing page that Goblin Horde already had, in the Horde window and on the viewer's own page, shows it to this computer when phone access is turned on, while it is on, and when a new code is made. A `pets-join` that fails saves nothing on the display. Its check pairs with the host, so it can leave the display a session there, which ends after a day or when the host turns the shared game off or makes a new code. `pets-adopt` copies only the saved game format's numbers and its date out of a file the person names, each held to what a game can reach, and saves the moment of adoption with the game as a cutoff: work that finished at or before it is never paid. That file must be a regular file on a local disk, named by its real path: the place the path really leads to, with every link and junction in it followed, must be the path itself. A network share, a drive letter or a folder whose real place is a share, a device, a folder, a link, a path through a link or a junction in any folder above the file, a file over 1 MB, and this computer's own saved game under another name are refused. A saved game that `--replace` replaces is kept as a copy with a name of its own, and no copy is written over. For tests, `GOBLIN_SHARED_LOOPBACK=<port>` replaces the tailnet with 127.0.0.1: the listener binds 127.0.0.1 on that port, answers loopback peers only, and asks Tailscale nothing, so it opens nothing that this computer could not already reach. Relevant issues include any route but the five answering on the shared listener, a request that passes with a peer outside Tailscale's ranges, another login, a wrong Host or Origin, or no session, the listener bound to any other address or open without the `tailscale` program, a listener that serves after the shared game was turned off, the pairing code or a session token in a log, an error, or an answer, however the code is spelled, anything but the game's own fields and codes reaching a display, a sentence a host sent being shown, a display sending the code off the tailnet, a file that holds the code readable by another account once sharing started, work from before an adoption being paid, a saved game replaced by a new game, an adoption that follows a link, and two viewers writing one saved game.
- **The task view.** `GET /api/tasks` and `GET /api/transcript` answer this computer only (403 for a paired phone). The task list reads the hook log, Codex's chat list, Orca's snapshot when it answers, and, to list Claude Code sessions the hook log does not hold, the file list under the Claude config folder's `projects` (links and junctions never followed) with the first and last 64 KB of each new or changed transcript and a subagent's `.meta.json`. A transcript is read only for the agent whose column is open, a page at a time, through the same confined locator as `/api/agent`; an output Claude Code saved in a `tool-results` file is read only when its real location is inside that `projects` folder. To group Orca workers with the Codex chat that started them, the task list also reads, in the background, the items of Codex chats active in the past two days through Codex itself, keeping from their Orca commands and those commands' JSON answers only run, task, and dispatch ids, a run's objective from `run-create`'s answer (credential-filtered, 200 characters), terminal handles, session ids a terminal screen showed, and 16-character hashes of words typed into a terminal; and, while Orca answers, Orca's own run and worker lists (read-only `orca orchestration run-list` and `worker-list`). Every text passes the credential filter, and nothing read is written anywhere; `task-links.json` in the state folder keeps only agent ids, Orca ids, those hashes, run objectives (credential-filtered, 200 characters), and link kinds. When Claude Code runs in an Orca terminal, the hook also records that terminal's Orca ids (handle, pane, worktree, workspace; shape-checked, at most 120 characters) and the Orca terminal handles each shell command directs. `POST /api/app/open` (and `node goblin.mjs app`) takes the same local, Origin, and JSON checks as the other local routes and opens only `http://127.0.0.1:<port>/app` with checked task and agent ids, in Edge or Chrome found in their install folders or the App Paths registry (or `GOBLIN_HORDE_APP_BROWSER`, an absolute path the person set), else the default browser, with a browser profile in the state folder; no shell. Relevant issues include a phone or another site reaching these routes, a transcript read outside the agent's own files, and a launch of any other address or program.
- **Agent detail and controls.** `GET /api/agent` reads one selected agent's own records on this computer (the newest part of a Claude Code transcript under the Claude config folder's `projects`, a Codex chat's newest turns and the plan in its session file, an Orca terminal's rendered screen, inbox, and task list, and the branch named in the agent's folder's `.git/HEAD`) and answers only requests from this computer. To name the Claude Code sessions the scene can show, the server also reads the last 64 KB of their transcripts through the same confined locator and keeps only a session title (a custom title, Claude Code's own title or summary, or the first line of the last prompt, credential-filtered). A transcript path recorded in the hook log is read only when its real location, with links and junctions followed, is inside that `projects` folder; a network share or device path (`\\server\share`, `//server`, `\\?\`, `\\.\`, `NUL`) is never touched, there or as an agent's folder; and an extension feed's folder is never read. `POST /api/open` and `POST /api/message` take the same local, Origin, and JSON checks as the other local-only routes; Open launches only `codex://threads/<id>` or `claude://code/continue?session=local_<id>` links (ids checked first, no shell) or `orca terminal switch`, and Message only the Codex reply path or `orca terminal send` with the text passed as one `--text=` argument. To find the Claude app's own id for a session, the server reads the Claude app's `claude-code-sessions` index files and keeps only their session ids and archived flag. Relevant issues include a phone or another site reaching any of these routes, detail text reaching a phone, these reads following a path outside those folders (an agent id or a recorded transcript path that escapes its session's own file), a launch of any other URL or program, and text reaching a terminal as more than one line or as a CLI flag.
- **Reply sending.** A paired device or web page causing replies to be sent to a Codex chat it should not reach.
- **Install, hooks, and uninstall.** The manager editing Claude Code settings beyond its own entries, stopping processes that are not this installation's own, or removing files outside its own install and state folders.
- **Packaging.** `scripts/package.mjs` letting local state, personal paths, or credentials into the ZIP.

## Out of scope / known limits

- **Plain HTTP on the local network.** Phone pairing uses HTTP, not HTTPS. Anyone who can watch traffic on the same network may see the pairing code or session cookie. Use phone pairing only on a network you trust; this is documented, not a vulnerability by itself.
- Anyone with the pairing code and network access, while phone access is on, can view the listed chats, send replies, and answer Codex approvals. That is the intended design; turn phone access off or make a new pairing code to end it. What a phone reads includes each chat's and session's name: a Claude Code session's name comes from the name you gave it, the session's title, or the first prompt you sent in it, credential-filtered and at most 60 characters. A Claude Code subagent reads only as its type ("Explore subagent") on a phone, never the task it was given, and the last line of a reply excerpt that was cut short is left out, since a question may start there.
- **Plain HTTP inside the tailnet.** The shared pet game's listener speaks HTTP and relies on Tailscale to encrypt and authenticate the traffic between the person's computers. Anyone signed in to the person's Tailscale account on a computer that holds the pairing code can read the game, buy, and fight. That is the intended design. The host does not listen without the `tailscale` program, because only that program can tell this computer's Tailscale address from an address in 100.64.0.0/10 that an internet provider handed out, and only it can name a caller's login. A proxy or port forward the person puts in front of the listener is outside what it can check. One writer of the saved game is enforced by a lock with a heartbeat, not by a lock of the operating system. A writer that is frozen for more than 20 seconds in the instant between its last lock check and its file rename could, in theory, still overwrite a newer save. Only an operating-system lock would close that. The listener's Tailscale address is checked when it opens and every 60 seconds, not continuously, so for up to a minute after Tailscale gives the computer another address the listener is still bound to the old one.
- **Other programs and accounts on the same computer are trusted.** "This computer" means a connection from `127.0.0.1`: any local process, including one running as another Windows, macOS, or Linux account on the same machine, can use the viewer the way you can, including the local-only routes. Multi-user computers (shared PCs, terminal servers) are out of scope for now; run Goblin Horde only on a computer whose other accounts you trust.
- The credential filter recognises common shapes and removes only the secret, keeping the words around it: `key=value` and `key: value` pairs whose key names a credential (password, pwd, passcode, secret, token, API, access, account, private, signing, encryption, client, master or subscription key, `db_pass`-style names, credential, authorization, cookie), quoted or bare (a path to a key file stays); a connection string's `Password=`/`Pwd=` up to the next `;`; the credential after any `Authorization:` scheme word (`Bearer`, `Basic`, `Bot`, `OAuth`, `AWS`, `SharedKey account:`, and others; a parameter list such as OAuth's or Digest's goes whole); password flags (`--password`, `-Password`, `--token`, keytool and jarsigner `-storepass`/`-keypass`, sqlcmd/bcp `-P` with the password apart or attached, mysql `-p…`, docker/podman login, `az login`, psexec and mongosh `-p`, sshpass `-p`, redis-cli `-a`, ldapsearch `-w`, openssl `-k`, zip `-P`, 7z `-p…`, cmdkey `/pass:`, schtasks `/rp`, `net use \\host\share <password>`, smbclient `-U user%…`, curl `-u user:…`); PowerShell `ConvertTo-SecureString "…"` (switches first or last) and `NetworkCredential("user", "…")` literals, PowerShell's backtick-escaped quotes included; shell and PowerShell assignments to variables named for a secret (`$pw = "…"`, `$dbPass='…'`, `export API_TOKEN=…`, `set PASSWORD=…`, `setx API_TOKEN "…"`, `[Environment]::SetEnvironmentVariable("API_TOKEN", "…")`, Python's `os.environ["API_TOKEN"] = "…"`); openssl `pass:…`; `aws configure set aws_secret_access_key …`; npm `:_authToken …`; the password in a URL (`user:…@host`); Slack and Discord webhook URLs; Azure SAS signatures; "the password is …" in prose; private key blocks; JWTs; well-known token prefixes (GitHub, GitLab, Slack, Stripe, npm, AWS access key ids, Google API keys, `sk-` keys); and long random strings (but not 40- or 64-character git ids). A variable reference (`$pw`, `"$PW"`, `%PW%`) or cmdlet (`Read-Host`) in those places names where a secret is, not the secret, and stays. A secret in an unusual shape can pass it; on this computer such text is visible to you (and a Claude Code command or prompt excerpt that held it is kept in the local activity file), and on a phone command output, tool arguments, and the words of asks (wherever they appear), current steps, and plans are left out entirely.
- Attacks that require an attacker already running code as your user on the computer, or control of your Codex, Claude Code, or Orca installation.
- Problems in Codex, Claude Code, Orca, Node.js, Python, or Tk themselves. Report those to their maintainers.

## Handling report data

Do not send real chat contents, pairing codes, Claude Code settings, tokens, or logs with personal paths, even privately, unless a maintainer specifically asks for something and you are comfortable sharing it. Invented data that reproduces the problem is almost always enough.
