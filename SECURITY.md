# Security policy

Goblin Horde runs on your own computer. Its pet game counts finished work from T3 Code's local database and draws goblins on your desktop. It can share one game between your own computers over Tailscale. We take reports about exposure seriously.

## Reporting a vulnerability

Please report privately first:

1. **Preferred:** use GitHub's private vulnerability reporting for this repository (**Security** tab, then **Report a vulnerability**) once it is enabled.
2. **If that option is not available yet:** open a regular issue titled "Security contact request" that says only which area is affected (for example "shared game listener" or "T3 Code reader"). **Do not include** exploit details, proof-of-concept code, or real data. A maintainer will reply with a private way to share the details.

Please give us a reasonable chance to fix the problem before disclosing it publicly. There is no bug bounty.

Supported version: the latest code on the `goblin-pets` branch, and the latest signed release, which installed copies with the updater take by themselves. Older ZIP packages are not patched separately. A copy installed before the updater existed has no updater: reinstall it from current source once.

## In scope

- **The local server.** The local server listens on `127.0.0.1` only. A second listener opens only when the person turns the shared game on, as described below. Relevant issues include any listener on a non-loopback address while the shared game is off, the server binding to a public address, and Host or Origin checks that let another site or device reach a route.
- **The pet game.** The local server reads T3 Code's own database (`~/.t3/userdata/statev2.sqlite`, or the file that `GOBLIN_T3_DB` names) read-only through the SQLite built into Node.js, and never writes it. Its one query selects statuses, finish times, ids, and token counts. The counts are taken out of T3 Code's JSON inside SQLite, so no prompt, message, title, or other payload text reaches JavaScript, and an id leaves the reader only as a 16-character hash. A database whose tables or columns are not the expected ones is not read at all. `doctor` opens the same database the same way and prints only the verdict and the file's path. The saved game (`pets.json` and `pets.json.bak` in the state folder) holds numbers, a date, and the hashes of the most recently paid work. Each number is held to what a game can reach: counts are whole numbers within fixed limits, amounts are at most a million million, and a saved game whose horde power or prices would not be numbers is not loaded. A count that only this game's size limits is cut down to it and never refused: more bosses cleared than the game has are held to the bosses there are, and a rerun of a boss the game no longer has is dropped. A saved game is never replaced by a new game. When `pets.json` cannot be read as a saved game and its backup can, the game goes on from the backup. When neither can, no game starts, the local server says so (`ready: false`), and nothing is written. A file that could not be read is kept, when a start is refused over it and before a save replaces it, as `pets.json.unreadable.<milliseconds>-<random letters>`: a copy with a name of its own, made only where no file has that name, made once for the same bytes, and private to this account, which it is made while it is still empty. A new game begins only in a state folder with neither `pets.json` nor `pets.json.bak`. `GET /api/pets`, `POST /api/pets/buy`, and `POST /api/pets/fight` answer this computer only, and the two POSTs need the server's own Origin and a JSON body. A paired computer on the person's tailnet reaches them only through the shared listener described below, and only once the person turned it on. Only one Goblin Horde runs a saved game: it holds `pets.lock` in the state folder (its process id, start time, and port, nothing else) and touches it every five seconds, and a second one on the same state folder never loads or saves the game. A lock that has shown an observer no heartbeat for 20 seconds is free whatever its process id says, since Windows hands a freed process id to the next program. A heartbeat is any change of the lock file's modified time, and the 20 seconds are counted on the observer's own monotonic clock. The file's date is never read as a time, so a date an hour ahead does not keep a lock and a date an hour behind does not free one. One look therefore never frees a lock whose process id is alive. Whoever asks for the lock watches it, a starting server and `pets-adopt` and `pets-host` alike: a holder that runs shows its heartbeat within five seconds and keeps the lock, and one that shows none for 20 seconds loses it. A server that stops gives the lock up only after its last save has landed, and a save asks for the lock again right before each file is put in place. So that goblins can stand on open windows, the pet field asks the Windows API which top-level windows are visible and where each one's rectangle is. For this it never copies a window's title and never asks for the name of the program that owns a window. It asks only how long a title is, compares a window's class with the shell's own classes and then drops it, and compares the owning process id with its own. A window is kept in memory as four numbers and a salted hash of its handle, with a new salt on every run, and nothing about windows is written to disk. The pet field also asks how long ago the last key press or pointer move was (a number of milliseconds, never which key), whether a full-screen window is in front, and where each display and its taskbar are. None of this is sent anywhere. Relevant issues include payload text, a window title, or a program name reaching JavaScript, the screen, a log, or the saved game; any write to T3 Code's database; another site or another device reaching the game's routes; and anything about the game leaving the computer outside the shared game.
- **The shared pet game.** Off by default. `pets-host enable` (`shared.json` in the state folder) makes the local server open one more listener, on this computer's own Tailscale IPv4 address (100.64.0.0/10) at the server's port. It never listens on a Wi-Fi or wired address or on every address, and a saved address that is no longer this computer's Tailscale address keeps it closed. The address is the one this computer's own `tailscale` program names: `tailscale ip -4` gives it, `tailscale status --json` must say Tailscale is connected and list the same address, and an adapter must have it. No adapter's name or address stands in for the program's word, because an internet provider can hand out addresses in the same range. When the `tailscale` program is not found or does not answer, there is no listener, and `pets-host enable`, `pets-host status`, and `doctor` say so. The address is asked for when the listener opens, which every start of Goblin Horde does, and again every 60 seconds while the listener is open. It is not watched in between: when Tailscale gives the computer another address, the listener closes at the next of those checks, the reason is logged, and it stays closed until `pets-host enable` is run again or the old address is back. It is a server of its own with its own handler, so it answers five routes and no other route the local server has: `POST /api/pair`, `GET /api/pets`, `POST /api/pets/buy`, `POST /api/pets/fight`, and `GET /api/pets/whoami` (which answers `{"ok":true}`). Every request must pass, in order: the peer address its socket reports is in 100.64.0.0/10 or fd7a:115c:a1e0::/48 (a forwarded header is never read); the Host header is the listener's address or one of the MagicDNS names `tailscale status` gives for this computer, with its port; the request's path, exactly as it was sent and with nothing normalized, is one of the five, so `/x/../api/pets`, `/api%2Fpets`, and `/api/pets/` are no route; `tailscale whois` names the peer's login as this computer's own, for every request (a verdict is kept for 60 seconds, a failed lookup refuses, and a tagged device never passes); a POST carries the listener's own Origin; and, for the three game routes, a session cookie earned at `POST /api/pair` with the pairing code (five wrong tries per address per ten minutes). Pairing is bounded: an address holds one session, at most 32 sessions live, an address may earn eight new sessions in ten minutes, and at most 1,024 addresses are tracked, where a full table refuses a new address and never forgets one that used up its tries. An address that is signed in and gives the code again is answered the session it has, with nothing new made and nothing counted. So the programs on one computer share one session, and the check `pets-join` makes never signs a running display out. `pets-host disable` is applied through the Goblin Horde that runs on the state folder, which the manager finds by `pets.lock`, by the last start's record, or on its own port. It reports that every computer is signed out only when that Goblin Horde's answer says all three things: the shared game is off, nothing listens, and no session is left. An answer that leaves one of them out confirms nothing. Every request the manager and the saved game's lock make to a local server on this computer has one deadline for the whole exchange, so a server that sends half an answer, or sends it a byte at a time, is given up on, and the manager changes nothing when a Goblin Horde holds the saved game and does not answer. A listener also reads `shared.json` again before every answer and every three seconds, and closes itself and ends its sessions once the file no longer turns it on, so a change made any other way takes effect too. A `shared.json` that cannot be read is not an off, since that is what a file looks like in the middle of a write: the last choice that could be read stands for 30 seconds while the file is read again every second. After that the listener closes and its sessions end, and it opens again once the file can be read and says on. What crosses the connection is, from a display, pairing requests (the pairing code in the body of `POST /api/pair`), the session cookie, the number of the last event it has shown, and game actions (the kind of a purchase, the number of a boss to fight), and, from the host, the game's three answers. Each answer is cut down to a fixed set of fields by the host before it is sent and again by the display before it is shown: numbers, true and false, a run's name of eight hexadecimal characters, a date, and short codes from fixed lists that say why a game is not ready, why work is not counted, or why a request was not done. No sentence crosses. A host sends a code and never its own words. On a display, a code that is not on its list reads "error", a sentence a host sent is dropped unread, and each code is said in a sentence of the display's own. For an answer with a sentence and no code, as a host of an older version sends, a display shows its own plain sentence and none of the host's words. An answer that holds the pairing code is not sent by a host and not passed on by a display. The code is looked for in every field's name, text, and number, with case, spaces, dashes, and every other character that is not a letter or a digit taken out first, and across the values that follow one another. A display (`pets-join`, which writes `remote.json` and `remote-code.txt`) opens no saved game and forwards its three local pets routes to the host. It sends the code only to a Tailscale address written as four plain decimal numbers, or to a name that resolves to one. A host written as any other kind of number (hexadecimal, octal, a single integer, a short form), an IPv6 address, or a name made only of digits and the letters a to f and x is refused before anything is sent, and the connection is made to exactly the host that was checked. A display never follows a redirect or uses a proxy, gives up on a host at one deadline whatever the host sends meanwhile (a `101` answer included), never repeats a host's own words in a message, takes the code from a file or standard input and never from the command line, and never logs or prints it. `remote-code.txt`, `pairing-code.txt`, and `shared.json` are written so that only this account can open them. The file's inherited permissions are removed with `icacls`, this account is given the file, and the permissions are read back before the text is written; when anyone but this account, SYSTEM, and Administrators is still in them, the file is not written. A file that was there already, left by an older version or another program with its folder's permissions, is made private where it is, and its permissions are read back: `pairing-code.txt` when the shared game is turned on, `pairing-code.txt` and `shared.json` every time before the shared listener opens, and `remote-code.txt` before a display that starts reads its code. When a file cannot be made private, the host does not listen, or the display shows no game and sends its host nothing, and each names the file. The pairing code leaves a computer in one way only: from a display to its host when it pairs, to an address checked as on the tailnet. It is shown on a screen only on the host itself, where `pets-host code` prints it to a terminal on this computer. A `pets-join` that fails saves nothing on the display. Its check pairs with the host, so it can leave the display a session there, which ends after a day or when the host turns the shared game off. `pets-adopt` copies only the saved game format's numbers and its date out of a file the person names, each held to what a game can reach, and saves the moment of adoption with the game as a cutoff: work that finished at or before it is never paid. That file must be a regular file on a local disk, named by its real path: the place the path really leads to, with every link and junction in it followed, must be the path itself. A network share, a drive letter or a folder whose real place is a share, a device, a folder, a link, a path through a link or a junction in any folder above the file, a file over 1 MB, and this computer's own saved game under another name are refused. A saved game that `--replace` replaces is kept as a copy with a name of its own, and no copy is written over. For tests, `GOBLIN_SHARED_LOOPBACK=<port>` replaces the tailnet with 127.0.0.1: the listener binds 127.0.0.1 on that port, answers loopback peers only, and asks Tailscale nothing, so it opens nothing that this computer could not already reach. Relevant issues include any route but the five answering on the shared listener, a request that passes with a peer outside Tailscale's ranges, another login, a wrong Host or Origin, or no session, the listener bound to any other address or open without the `tailscale` program, a listener that serves after the shared game was turned off, the pairing code or a session token in a log, an error, or an answer, however the code is spelled, anything but the game's own fields and codes reaching a display, a sentence a host sent being shown, a display sending the code off the tailnet, a file that holds the code readable by another account once sharing started, work from before an adoption being paid, a saved game replaced by a new game, an adoption that follows a link, and two Goblin Horde copies writing one saved game.
- **Updates.** A release is code that will run on the person's computers, so nothing about where it came from is trusted. Trust comes from an Ed25519 signature made with a private key that exists only on the release author's computer. Its public half ships in every build as `lib/update-key.mjs`, and a build whose key is empty refuses every update with "This build has no update key, so it cannot check for updates." The local server looks for a release two minutes after it starts and then about once a day, unless `update --off` turned that off (`updates/settings.json` in the state folder); `update` looks when the person runs it. The only requests are to `https://github.com/epoisel/goblin-horde/releases/download/pets-latest/update.json` and `.../GoblinHorde-Team.zip`, on a rolling pre-release that is never the repository's "Latest" release (that one belongs to the earlier monitor app). The addresses are fixed in the code and no setting or environment variable changes them. Redirects are followed one at a time, at most five, and every address asked must be `https:` on `github.com`, `githubusercontent.com`, or a name under them. Each request has 30 seconds, `update.json` may be at most 16 KB and the ZIP at most 25 MB, and the only header of Goblin Horde's own is `User-Agent: GoblinHorde/<installed version>`. One function checks every release, for the daily check, `update`, the next start, `update --rollback`, and the release build checking its own output. Each check runs only once those before it passed, and any failure stops with a sentence and writes nothing but the time and reason of the check, except that a kept release that fails its check again at a start is deleted: (1) the build has a key; (2) `update.json` has `format` 1, a plain `x.y.z` version, the package name `GoblinHorde-Team.zip`, a size up to 25 MB, a lowercase SHA-256, and a 64-byte signature; (3) the signature verifies with the build's key over the exact text `goblin-horde-update\nformat=1\nversion=<version>\nsize=<size>\nsha256=<sha256>\n`; (4) the version is newer than the installed one and than a version skipped on this computer, or, for `--rollback` only, older; (5) the ZIP has exactly the signed size and SHA-256, and it is not downloaded before 1 to 4 pass; (6) the ZIP is read in memory by a strict reader that takes one disk, no comment, no ZIP64, no encryption, no data descriptors or extra fields, stored or deflated entries only, at most 200 entries, and at most 60 MB declared, which is checked before anything is inflated; each entry must inflate to exactly its declared size and checksum, every name must be plain printable ASCII under the top `GoblinHorde/` folder, with no backslash, colon, drive letter, `..`, `.`, empty part, part ending in a dot or space, or Windows device name, and no two names may be the same file to Windows; every entry must be listed in the package's own `package-files.json` and every listed file present; and its `package.json` must carry the signed version. Only then is the release written, to a new folder under the state folder (`updates/ready/<version>/`), never over the installation. At the next start, while nothing of the installation runs, the release is moved into a folder of the apply's own, checked again from its own bytes in full, unpacked beside a whole copy of the installed files, and only then is the installation stopped and the release's own manager run with `install --no-start`, then `start`. It counts as in place once the local server answers with the new version. When the install or the start fails, the copy's own manager puts the earlier version back, it is started, and the failed version is skipped (`updates/skip.json`); an apply cut short by a stopped process is finished or undone at the next start, judged by the installation's marker, which install writes last. One apply runs at a time, under `updates/apply.lock`. The saved game, `goblins.json`, `shared.json`, the locks, and the pairing files are never opened by an update. The kept zip of the release installed before (`updates/previous/`) is checked again in full before `--rollback` uses it. The desktop goblins put a waiting release in place through `POST /api/update/apply`, which answers this computer only, needs the server's own Host, Origin, and a JSON body, takes nothing from the request, and starts only this installation's own manager. `GET /api/pets` names a waiting release's version only to this computer: the shared listener has no update route and its game answers carry no update field. Relevant issues include a release accepted without a valid signature from the build's key, a request to any other address or over plain HTTP, a file of a release written outside its package folder or before every check passed, an update that changes the saved game or the settings, a route reachable from another computer or another site that starts an update, and an older release put in place other than by `--rollback`.
- **Release tooling.** `scripts/release.mjs keygen` writes the private key once, to a file made private to this account before the key is in it, refuses to write over a file, never prints the key, and refuses to replace a public key that `lib/update-key.mjs` already holds. `build` refuses a signing key that is not the other half of that public key, and removes its output when it does not pass the installations' own check. `publish` runs `gh` only with `--run`. Relevant issues include the private key reaching the package, a log, or any output.
- **Install and uninstall.** The manager stopping processes that are not this installation's own, or removing files outside its own install and state folders. Install, start, and uninstall take out the Claude Code settings entries that an earlier build of this installation added, and keep every other setting and a backup. Relevant issues include the manager changing Claude Code settings beyond this installation's own entries.
- **Packaging.** `scripts/package.mjs` letting local state, personal paths, or credentials into the ZIP.

## Out of scope / known limits

- **Plain HTTP inside the tailnet.** The shared pet game's listener speaks HTTP and relies on Tailscale to encrypt and authenticate the traffic between the person's computers. Anyone signed in to the person's Tailscale account on a computer that holds the pairing code can read the game, buy, and fight. That is the intended design. The host does not listen without the `tailscale` program, because only that program can tell this computer's Tailscale address from an address in 100.64.0.0/10 that an internet provider handed out, and only it can name a caller's login. A proxy or port forward the person puts in front of the listener is outside what it can check. One writer of the saved game is enforced by a lock with a heartbeat, not by a lock of the operating system. A writer that is frozen for more than 20 seconds in the instant between its last lock check and its file rename could, in theory, still overwrite a newer save. Only an operating-system lock would close that. The listener's Tailscale address is checked when it opens and every 60 seconds, not continuously, so for up to a minute after Tailscale gives the computer another address the listener is still bound to the old one.
- **Other programs and accounts on the same computer are trusted.** "This computer" means a connection from `127.0.0.1`. Any local process, including one running as another Windows account on the same machine, can use the local server the way you can, including the local-only routes. Multi-user computers (shared PCs, terminal servers) are out of scope for now. Run Goblin Horde only on a computer whose other accounts you trust.
- **The signing key is the root of trust for updates.** Whoever holds the private key can sign a release that every installed copy runs at its next start. Keeping it safe and offline-backed is the release author's job. There is no way to revoke a key: replacing it needs a release signed with the old key, or a manual install on each computer. A release is taken from the repository's latest GitHub release, so a release of another app published on the same repository as the latest would stop updates until the next pet game release (the copies refuse it, since it carries no `update.json` signed with their key). A signed release cannot be replaced by an older signed release, except through `update --rollback` of the one kept on that computer.
- Attacks that require an attacker already running code as your user on the computer, or control of your T3 Code or Tailscale installation. That includes writing into the state folder, where downloaded releases wait: each is checked again in full before it is used, but code running as you could change the installed app directly.
- Problems in T3 Code, Tailscale, Node.js, Python, or Tk themselves. Report those to their maintainers.

## Handling report data

Do not send real chat contents, pairing codes, saved games, tokens, or logs with personal paths, even privately, unless a maintainer specifically asks for something and you are comfortable sharing it. Invented data that reproduces the problem is almost always enough.
